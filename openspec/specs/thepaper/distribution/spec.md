# thepaper/distribution Specification

## Purpose

Определяет упаковку `thepaper` как пакета Nix и доставку готового ELF через GitHub Releases: установку из флейк-ссылки без компиляции Rust, сборку из исходников, проверки CI и неизменяемый релиз.

## Requirements

### Requirement: Пакет Nix

Флейк ДОЛЖЕН предоставлять `packages.x86_64-linux.default`, `packages.x86_64-linux.thepaper` и `packages.x86_64-linux.source`. `default` и `thepaper` ДОЛЖНЫ указывать на один пакет; при наличии `release.json` он скачивает ELF по `url` и проверяет его по `hash`, НЕ ДОЛЖЕН компилировать Rust и ставит `bin/thepaper`, обёрнутый с `ffmpeg`, `ffprobe` и `vainfo` в `PATH`. `source` ДОЛЖЕН собираться из `Cargo.lock`, прогонять тесты и ставить тот же интерфейс с ELF в `libexec/thepaper`. Оба пакета ДОЛЖНЫ использовать один набор зависимостей, включая один атрибут FFmpeg, и ДОЛЖНЫ добавлять в RPATH каталоги библиотек, загружаемых через `dlopen` (Vulkan loader, libglvnd), а не только ссылки `DT_NEEDED`. Версия `source` ДОЛЖНА совпадать с `Cargo.toml`; версия `default` ДОЛЖНА совпадать с `release.json`, а `thepaper --version` из пакета — с версией пакета. Пока `release.json` отсутствует, `default` ДОЛЖЕН совпадать с `source` (bootstrap).

#### Scenario: Установка готового бинаря

- **WHEN** чистая машина с Nix и сетью выполняет `nix profile add github:afaser/thepaper` при наличии `release.json`
- **THEN** в логе установки есть скачивание ассета и `autoPatchelf`, нет вызовов `cargo` и `rustc`, `thepaper --help` работает, а `thepaper --version` совпадает с `release.json.version`

#### Scenario: Сборка из исходников

- **WHEN** выполняется `nix build .#source` в чистом клоне
- **THEN** тесты прогоняются, результат содержит `bin/thepaper` и `libexec/thepaper`, `source.version` равен `Cargo.toml`, а `result/bin/thepaper --version` совпадает с ним

#### Scenario: Инструменты и библиотеки в окружении пакета

- **WHEN** пакет установлен на машине без `ffmpeg`, `ffprobe` и `vainfo` в глобальном `PATH`
- **THEN** инструменты находятся из замыкания пакета, а `patchelf --print-rpath` для ELF содержит каталоги `vulkan-loader` и `libglvnd`

#### Scenario: Первый релиз ещё не выпущен

- **WHEN** `release.json` отсутствует
- **THEN** `nix build .#default` собирает пакет из исходников, и установка не падает на отсутствующем ассете

#### Scenario: Версия после повышения в Cargo.toml

- **WHEN** в `Cargo.toml` уже `0.2.0`, а `release.json` ещё описывает `0.1.0`
- **THEN** `source.version` равен `0.2.0`, `default.version` равен `0.1.0`, и установка из `trunk` продолжает ставить прежний релиз без ошибки версии

### Requirement: Переносимый вход флейка

Входы флейка НЕ ДОЛЖНЫ ссылаться на локальные пути файловой системы (`path:` или абсолютный `/nix/store/...`). `flake.lock` ДОЛЖЕН фиксировать ревизию nixpkgs, доступную для скачивания с GitHub. `release.json` ДОЛЖЕН содержать абсолютный HTTPS-URL ассета GitHub Release и его хеш в SRI. Оценка и сборка флейка ДОЛЖНЫ работать на чистой машине без предварительно скачанного nixpkgs.

#### Scenario: Сборка на чистой машине

- **WHEN** чистая машина с Nix и сетью выполняет `nix build github:afaser/thepaper#default`
- **THEN** nixpkgs скачивается по зафиксированной в `flake.lock` ревизии, ассет — по URL из `release.json`, и пакет собирается без правки флейка

#### Scenario: Локальный путь в lock-файле

- **WHEN** `flake.lock` содержит вход с `"type": "path"`
- **THEN** CI ДОЛЖЕН падать на проверке флейка, а не пытаться собрать такой вход

### Requirement: CI на push и pull request

На каждый push в `trunk` и каждый pull request ДОЛЖЕН запускаться workflow, который проверяет отсутствие `path`-входов, собирает `source` и `default`, выполняет `nix flake check` и сверяет `--version` установленного пакета с `default.version`. Провал любой проверки ДОЛЖЕН делать workflow неуспешным. Сборка pull request из форка НЕ ДОЛЖНА требовать секретов репозитория.

#### Scenario: Некомпилируемое изменение

- **WHEN** pull request содержит синтаксическую ошибку в `src/`
- **THEN** workflow завершается ошибкой на сборке `source`

#### Scenario: Корректное изменение

- **WHEN** pull request собирается, проходит `nix flake check`, а `result/bin/thepaper --help` и сверка версии успешны
- **THEN** workflow завершается успешно

#### Scenario: Pull request из форка

- **WHEN** pull request пришёл из форка без секретов репозитория
- **THEN** сборка и проверки выполняются без записи в GitHub и без падения из-за отсутствия секрета

### Requirement: Неизменяемый релиз

Ручной release-workflow ДОЛЖЕН принимать версию и запускаться на выбранной ветке. Он ДОЛЖЕН отказывать, если версия не совпадает с `Cargo.toml`. При отсутствии опубликованного релиза `vX` workflow ДОЛЖЕН собрать `source`, создать архив `thepaper-x86_64-linux.tar.gz` с ELF, вычислить SRI-хеш, проверить бинарный пакет из локального архива, записать `release.json`, создать коммит-пин и тег `vX`, создать draft-релиз с `--verify-tag`, загрузить ассет, опубликовать релиз, проверить установку по публичному URL и только затем отправить пин-коммит в ветку запуска. Тег и ассет опубликованного релиза НЕ ДОЛЖНЫ изменяться или удаляться: повторный запуск той же версии НЕ ДОЛЖЕН пересобирать или перезаписывать ассет, он может только довести отправку уже существующего пин-коммита быстрым-forward, если ветка не ушла вперёд. Ошибка до публикации ДОЛЖНА удалять только созданные этим запуском draft и тег; ошибка после публикации НЕ ДОЛЖНА удалять релиз и НЕ ДОЛЖНА отправлять пин в ветку. Одновременные запуски ДОЛЖНЫ сериализоваться. Любое изменение бинарного пакета, включая обновление nixpkgs, ДОЛЖНО выпускаться новой версией.

#### Scenario: Первый релиз версии

- **WHEN** release-workflow запущен на `trunk` с версией `0.1.0` при версии `0.1.0` в `Cargo.toml`
- **THEN** публикуется `v0.1.0` с архивом, тег `v0.1.0` указывает на коммит с `release.json`, `trunk` получает этот коммит, а установка из `trunk` и с тега ставит ELF без компиляции Rust

#### Scenario: Несовпадающая версия

- **WHEN** release-workflow запущен с версией `9.9.9` при версии `0.1.0` в `Cargo.toml`
- **THEN** workflow завершается ошибкой до сборки, релиз и тег не создаются

#### Scenario: Ошибка до публикации

- **WHEN** draft создан и ассет загружен, но публикация не удалась
- **THEN** draft и созданный этим запуском тег удаляются, пин-коммит не отправляется в ветку, прежний релиз продолжает работать

#### Scenario: Ошибка после публикации

- **WHEN** релиз опубликован, но отправка пин-коммита в ветку отклонена
- **THEN** релиз и тег остаются, ветка не меняется, а повторный запуск доводит только fast-forward отправку существующего пин-коммита

#### Scenario: Повторная попытка с изменённым исходником

- **WHEN** релиз `v0.1.0` уже опубликован, ветка ушла вперёд, и запуск снова требует `0.1.0`
- **THEN** workflow не пересобирает и не перезаписывает ассет, не переносит тег и завершается ошибкой, требуя новую версию

#### Scenario: Обновление nixpkgs

- **WHEN** ветка обновляет `flake.lock` и `Cargo.toml` до `0.1.1`, после чего release-workflow запускается с `0.1.1` на этой ветке
- **THEN** публикуется `v0.1.1` с бинарём, собранным из новых зависимостей, пин попадает в ветку, и `checks.default` проходит до слияния

#### Scenario: Одновременные запуски

- **WHEN** два release-workflow запущены одновременно
- **THEN** второй ждёт завершения первого и видит его опубликованный релиз или ошибку, но не загружает второй ассет с тем же именем
