## Context

Мотивация — proposal.md, Why. Проект пустой: ни крейта, ни зависимостей. Целевое окружение: niri (layer-shell, не на wlroots), libav/FFmpeg с VA-API, Vulkan на DRM render node, gamemoded на сессионной шине. Исходное видео 2K@15 fps. Требования — `specs/video-wallpaper/*/spec.md`. Среда разработки — Nix flake + direnv (D8).

Ориентир по замеру: предыдущая схема (VA-API decode → copy в RAM → software render → `Queue::write_texture`) дала ~60% CPU на одном ядре при 2K@15 fps; `mpv --vo=gpu-next --hwdec=vaapi` на том же файле — ~2%. Причина — покадровое преобразование/копирование в RAM. Поэтому выбран zero-copy GPU-конвейер: кадр от декодера сразу попадает в показ через разделяемый GPU-буфер.

## Goals / Non-Goals

**Goals:**

- Ровно один аппаратный декодер; кадр не копируется в системную память (zero-copy).
- Декодирование, цветовое преобразование, масштабирование и блюр — на GPU (Vulkan).
- Одна исходная GPU-текстура кадра на 4 поверхности: фон — кадр как есть, овервью — заблюренная версия того же кадра (кеш по кадру, блюр только при открытом овервью).
- niri IPC (`OverviewOpenedOrClosed`) и gamemode D-Bus без ручных действий.
- Vulkan-бэкенд принудителен: wgpu настраивается на Vulkan-адаптер, GL и software-пути исключены.
- Ограниченный RSS: bounded-очереди, никаких полнокадровых CPU-буферов и per-output промежуточных копий; во время игры лишние буферы освобождаются и heap возвращается ОС.
- Демон не конкурирует за ресурсы: постоянные `nice 19` и idle I/O, `SCHED_IDLE` на время игры.

**Non-Goals:**

- Программный декод и любой покадровый readback кадра в RAM (это и есть причина ~60% CPU).
- Поддержка композиторов, отличных от niri.
- NVIDIA/NVDEC/CUDA-путь на первом этапе (приоритет VA-API; см. риски).
- Выбор видео/плейлисты/GUI, звук.
- Изменение радиуса блюра и прочего конфига в рантайме (только при старте).
- Flatpak-портал gamemode (`org.freedesktop.portal.GameMode`): только прямой сервис `com.feralinteractive.GameMode`.
- Буквальное сжатие RAM/zram/компрессия кадров в рантайме: тратит CPU; вместо этого освобождение буферов и `malloc_trim`.
- root/CAP_SYS_NICE и управление GPU-приоритетом.

## Decisions

### D1: Декод — libav/FFmpeg + VA-API, вывод DMA-BUF (DRM_PRIME)

Один `AVFormatContext` (демультиплексор) + один `AVCodecContext` + один `AVHWDeviceContext(VAAPI)` на DRM render node. Аудиопоток пропускается. Декодер создаётся с `hwaccel=vaapi`; вывод кадров — `AV_PIX_FMT_DRM_PRIME` (через `hwaccel_output_format`/map VAAPI→DRM_PRIME). Кадр приходит как `AVDRMFrameDescriptor`: объекты с `fd`/`modifier`/`pitch`/`offset` по плоскостям.

Программный декод в рантайме запрещён: если hwaccel не поднялся или кадр пришёл не в DRM_PRIME/VAAPI — внятная ошибка и остановка.

Если кодек исходника не поддержан аппаратным декодером, система однократно транскодирует видео в **наиболее эффективный из реально поддерживаемых** аппаратных кодеков — без фиксированной цепочки «HEVC→AVC→VP9».

Опорные данные (для 2K):

| Кодек | Эффективность сжатия | Аппаратный декод VA-API | Энкодинг |
| --- | --- | --- | --- |
| AV1 | лучшая (~30%+ против AVC) | Intel Tiger Lake+/AMD RDNA2+/NVIDIA RTX 30+ | редко аппаратно (`av1_vaapi`: Intel Arc/TGL+, свежий NVIDIA), чаще SVT-AV1/rav1e на CPU (медленно) |
| HEVC | заметно лучше AVC (~15–30%) | Intel Skylake+/AMD GCN+/NVIDIA GTX 950+ | `hevc_vaapi` (QSV/VCE/NVENC) или `libx265` |
| VP9 | между AVC и HEVC | Intel Broadwell+/AMD RDNA1+/NVIDIA GTX 900+ | `vp9_vaapi` (ограниченно) или `libvpx-vp9` |
| H.264 | базовая | повсеместно | `h264_vaapi` или `libx264` |

Порядок выбора:
1. Перечислить профили декода и энкодера на целевом render node (через libva/пробу hwaccel, вспомогательно `vainfo`).
2. Оставить только кодеки с профилем аппаратного декода.
3. Среди них — максимум эффективности сжатия при наличии энкодера: приоритет аппаратному (`*_vaapi`), иначе CPU-энкодер с приемлемым временем (для одноразового энкода); при равной эффективности — более быстрый энкодер.
4. Залогировать решение с обоснованием (кодек, профиль декода, энкодер, причина).
5. Кэш — по исходнику (путь+mtime+размер) + целевой кодек/энкодер/настройки; переиспользовать между запусками.

Конфиг может явно задать `transcode_codec`, переопределяя автож.

Проверено на целевой машине (AMD Cezanne / VCN 3.0, Mesa `radeonsi`, VA-API 1.23, `renderD128`): декод H.264/HEVC/VP9 — работает, AV1 — «No support for codec av1»; энкод `h264_vaapi`/`hevc_vaapi` — работает, `vp9_vaapi` и `av1_vaapi` — «No usable encoding entrypoint/profile». Для AV1-исходника автовыбор, таким образом, = **HEVC + `hevc_vaapi`** (декод и энкод аппаратные, эффективность выше AVC/VP9).

Альтернативы:
- mpv/libmpv: upstream libmpv не отдаёт кадры наружу в Vulkan/zero-copy (render API — только OpenGL и software; Vulkan есть только в форках), а SW/GL-путь даёт именно тот readback, что измерен (~60% CPU). Отклонён.
- GStreamer (vaapi): рабочий, но тяжёлая инфраструктура и лишние слои для одной задачи; отклонён в пользу прямого libav.
- Vulkan Video (`VK_KHR_video_*`): поддержка драйверами неравномерна, Rust-биндингов нет; отложено.
- AV1 без VA-API: целевой сценарий — однократное транскодирование в HEVC/AVC (см. выше); более дорогая альтернатива — Vulkan Video (`VK_KHR_video_decode_av1`), если драйвер её предоставляет, но сейчас отложена.

### D2: Импорт DMA-BUF в Vulkan и рендер через wgpu

wgpu-устройство создаётся только на Vulkan-адаптере (`Backends::VULKAN`, без GL-фолбэка); запрашивается feature `VULKAN_EXTERNAL_MEMORY_DMA_BUF`. Для каждой плоскости кадра (Y и UV у NV12/P010) fd из `AVDRMFrameDescriptor` импортируется текстурой через `wgpu::hal::vulkan::Device::texture_from_dmabuf_fd(fd, desc, modifier, stride, offset)`; владение/lifetime — DropCallback + `on_submitted_work_done`.

Единый рендер-проход: семплирование Y/UV, цветовое преобразование (матрица по метаданным кадра), cover-масштабирование под выход; для блюр-поверхностей — сепарабельный гаусс (2 прохода, радиус из конфига) с кешем по номеру кадра. Блюр запускается только если блюр-поверхность видима и декод не на паузе. Фон сэмплирует текстуру кадра без блюра.

Синхронизация VAAPI→Vulkan — отдельный риск (см. Risks) и ранний спайк.

### D3: Layer-shell через SCTK (без wlroots)

Поверхности создаются через `smithay-client-toolkit` (SCTK 0.21): `LayerShell` + `LayerSurface` (биндинги `zwlr_layer_shell_unstable_v1`); зависимостей от wlroots нет — niri реализует протокол сам (Smithay). Своих XML/биндингов не пишем.

На каждый выход (`wl_output` из registry):
- фоновая поверхность: слой `background`, exclusive zone 0, mapped всегда;
- поверхность овервью: тот же слой `background`, выше живой, mapped только в овервью. Слой `top`/`overlay` не используем — он перекрыл бы окна и бары.

Идентификация: `app_id`/namespace = `<prefix>-live-<output>` и `<prefix>-blur-<output>`. Это единственный внешний контракт для правил niri.

Презентация: Vulkan-поверхность (wgpu `Surface`) из `wl_surface` layer-роли через raw window handle; требуется драйвер с `VK_KHR_wayland_surface`. Фолбэк при недоступности — DMA-buf/shm мост; см. Risks.

Горячее подключение/отключение выходов: трекинг `wl_output`, пары поверхностей создаются/уничтожаются на лету.

### D4: Овервью через niri IPC (крейт `niri-ipc`)

Используем официальный крейт `niri-ipc` (26.x, репозиторий niri-wm/niri): подключение к сокету из `NIRI_SOCKET`, `Request::EventStream` для подписки, событие `niri_ipc::Event::OverviewOpenedOrClosed { is_open }`. На старте дополнительно запрашиваем текущее состояние овервью. Своего JSON-парсера IPC не пишем.

Обработка:
- открытие → замапить блюр-поверхности на всех выходах и снять заморозку (рендер с блюром);
- закрытие → размапить (unmap) и заморозить (прекратить рендер/блюр, буфер остаётся последним).

Заморозка не трогает фоновые поверхности: они продолжают получать живой кадр, пока декод не на паузе из-за игры.

Разрыв/отсутствие канала → базовое состояние (только фоновые), реконнект при появлении.

### D5: Игра через D-Bus gamemode

`zbus` (6.x) на сессионной шине: прокси к `com.feralinteractive.GameMode`, подписка на сигналы `GameRegistered(pid, path)` / `GameUnregistered(pid, path)`; ведём множество зарегистрированных PID. Не пусто ⇒ пауза декода; пусто ⇒ снять паузу.

Фолбэк: polling property `ClientCount` (интервал ~1 s), если сигналы не приходят/сервис старая версия. Сервис недоступен ⇒ считаем, что игр нет.

Приоритет: игра > овервью. Во время игры декод стоит, даже если овервью открыт; после игры возобновление происходит по факту закрытия овервью/отсутствия игры.

### D6: Структура и конфигурация

Один бинарник, модули: `decoder` (libav/VA-API, demux, dma-buf), `render` (wgpu/Vulkan: импорт, цвет, блюр, поверхности), `compositor` (SCTK/layer-shell, outputs), `niri`, `gamemode`, `config`.

Конфиг TOML: `video_path` (обязательный), `blur_radius` (дефолт 12), `app_id_prefix`. Видео один файл на все выходы (условие задачи), без per-output маппинга.

### D7: Крейты вместо самописных обёрток

| Область | Крейт |
| --- | --- |
| декод | `ffmpeg-next` 9.x (+ `ffmpeg-sys-next`), libav с VA-API |
| GPU/рендер | `wgpu` с принудительным Vulkan-бэкендом + `wgpu-hal` (импорт DMA-BUF) |
| Wayland / layer-shell | `smithay-client-toolkit` 0.21 (+ `wayland-client`) |
| D-Bus | `zbus` 6.x |
| niri IPC | `niri-ipc` 26.x |
| async runtime | `tokio` 1.x |
| конфиг | `serde` + `toml` |
| CLI | `clap` 4.x |
| логи | `tracing` |
| ошибки | `anyhow` / `thiserror` |
| Linux scheduling / heap trim | `libc` (`setpriority`, `sched_setscheduler`, `ioprio_set`, `malloc_trim`) |

Отклонено: `rsmpv`/`libmpv2`/`mpv` (нет подходящего zero-copy/Vulkan пути; SW/GL — это и есть отвергнутый readback), `wgpu-dmabuf` 0.1.0 (115 загрузок, solo — берём `wgpu-hal` напрямую), `rsmpeg` (меньше контроля над hwaccel/dmabuf), GStreamer (тяжелее), `ash`/`vulkanalia` как обязательные (wgpu-Vulkan покрывает задачу; при необходимости — точечные вызовы через hal).

### D8: Окружение — Nix flake + direnv

Вся среда объявлена в `flake.nix`: devShell с Rust-тулчейном (`rustc`/`cargo`), FFmpeg/libav с VA-API, `libva`, Vulkan loader, `pkg-config`, wayland-библиотеками; `flake.lock` коммитится. `.envrc` содержит `use flake`. Любые команды проекта (сборка, проверки, тесты) запускаются через `direnv exec . <cmd>`; `nix develop` не используется. Нативные зависимости берём из `buildInputs`/`nativeBuildInputs` flake, а не из системного PATH вручную.

### D9: Ограничение RAM и низкий приоритет

**Память в обычном режиме.** Полнокадровых буферов в системной памяти нет: демультиплексор имеет ограниченную очередь пакетов, декодер — фиксированное кольцо из 3 DMA-BUF кадров. Все поверхности сэмплируют один исходный GPU-кадр; блюр кешируется один раз на номер кадра в одной GPU-текстуре, а не копируется для каждого выхода. Swapchain/present-буферы ограничены поверхностями выходов; никаких неограниченных очередей «на будущее».

**Во время игры.** После остановки чтения пакетов освобождаются очередь демультиплексора, неиспользуемые кадры кольца и временные ресурсы транскодирования. Сохраняются только состояние `AVCodecContext`/позиция видео, последний исходный GPU-кадр и, если овервью открыт, последний кеш блюра — иначе поверхности не смогли бы показать последний кадр. После освобождения вызывается glibc `malloc_trim(0)`, чтобы вернуть неиспользуемые heap-страницы ОС. Это уменьшение RSS, а не буквальное сжатие памяти: компрессия кадров/zram в рантайме потребляла бы CPU и не нужна.

**Приоритет.** В `main`, до создания рабочих потоков, вызываются `setpriority(PRIO_PROCESS, 0, 19)` и `ioprio_set(..., IOPRIO_CLASS_IDLE)`: потоки наследуют низкий приоритет. Во время игры каждый зарегистрированный рабочий поток переводится через `sched_setscheduler` в `SCHED_IDLE`; после игры — обратно в `SCHED_OTHER`. Значение nice 19 остаётся постоянным: непривилегированный процесс не смог бы вернуть его к 0. Ошибки смены политики логируются, но не мешают главному механизму — полной паузе декода. root/CAP_SYS_NICE не нужен; GPU-приоритетом демон не управляет.

## Risks / Trade-offs

### Блокирует: сначала вертикальный спайк
- [VAAPI→Vulkan interop на целевом железе не проверен: Mesa VCN3 отдаёт DRM_PRIME с модификаторами/планами, а `wgpu-hal::texture_from_dmabuf_fd` может их не принять или не синхронизировать] → первый шаг — минимальный бинарник: hw-декод H.264 → импорт dmabuf в wgpu-текстуру → один layer-surface; проверить картинку, артефакты, утечки. При провале — альтернативы: выделять dmabuf силами Vulkan и передавать во VAAPI (DRM frames context), DRM syncobj/sync_file.
- [Синхронизация: VAAPI пишет кадр внешней памятью, ffmpeg не даёт semaphore; преждевременное переиспользование/закрытие fd] → барьеры + `on_submitted_work_done`, ring ≥ 3, fd закрывать только после GPU-работы; тест на артефакты под нагрузкой.
- [niri IPC: `OverviewOpenedOrClosed` есть только в свежих niri (PR #1526, май 2025); версия `niri-ipc` должна совпадать с установленным niri] → проверить `niri --version` и событие на старте; при несовпадении — явная ошибка/деградация, а не тишина.

### Поток кадров и форматы
- [VAAPI multi-planar (NV12/P010), `texture_from_dmabuf_fd` single-plane] → импортировать плоскости раздельно (R8/RG8), конвертировать в шейдере.
- [Формат/цвет: limited/full range, BT.601/709/2020, 8/10-бит, поворот/crop, color-management-v1] → брать из метаданных кадра, проверять на эталонном кадре; неверная матрица = «зелёные»/вымытые цвета.
- [Vulkan-устройство ≠ VAAPI-устройство (гибрид/внешняя GPU)] → привязать оба к устройству композитора (render node/dmabuf feedback), иначе импорт чужих dmabuf может не поддерживаться.
- [Модификатор/формат DMA-BUF не поддерживается композитором или драйвером] → согласование через linux-dmabuf feedback; при неудаче — внятная ошибка, не молчаливый fallback.

### Поверхности и композитор
- [Видимость background-слоя в овервью niri не подтверждена: если фон не рендерится под превью, блюр-поверхность будет невидна] → проверить на реальной системе в спайке; если слой `background` в овервью не виден, это блокер: зафиксировать ограничение и запросить решение, а не молча переходить на `top`/`overlay`/toplevel.
- [Vulkan surface из wl_surface layer-роли: `VK_KHR_wayland_surface`, размер/scale, anchor всех рёбер, exclusive_zone=0] → фолбэк DMA-buf/shm.
- [Хоткплуг/смена scale: пересоздание поверхностей, гонки при уничтожении output] → трекинг в compositor-модуле, уничтожение после drain.
- [Создание wgpu-поверхности из `wl_surface` layer-роли не работает на части драйверов] → фолбэк: DMA-buf (`VK_EXT_external_memory_dma_buf` + `zwlr_linux_dmabuf_v1`) либо shm-мост.

### Управление и жизненный цикл
- [Два инстанса (автозапуск + ручной запуск) → двойной декод] → `flock`-лок, второй выходит с сообщением.
- [Пауза по gamemode не останавливает декод, если глушить только рендер] → пауза на уровне чтения пакетов; проверить падение CPU.
- [Busy-loop между кадрами/событиями] → event loop с ожиданием (condvar/таймер ~1/fps), не spin.
- [EOF/seek: mkv/webm seek может не попадать или возвращать ошибку] → тест на реальном файле; фолбэк — переоткрытие файла.
- [Гонки overview toggle/map-unmap/blur-cache] → единое состояние, атомарный переход, инвалидация устаревших кадров.
- [Блюр на GPU тратит GPU-время] → только при видимой блюр-поверхности, кеш по кадру; вне овервью проходы не запускаются.

### Зависимости и конфигурация
- [nixpkgs ffmpeg может быть собран без VAAPI/libva] → проверить `-hwaccels`/`vainfo` в devShell; при необходимости `ffmpeg-full`; Vulkan loader и pkg-config для libav+libva.
- [Транскод: `hevc_vaapi` работает на малом клипе, но на 2K возможны лимиты разрешения/битрейта/10-bit] → проверить на целевом разрешении; CPU `libx265` фолбэк; следить за местом/ротацией кеша.
- [gamemoded может отсутствовать или быть Flatpak-портал; сигналы могут отличаться по версиям] → недоступность = игр нет; polling `ClientCount`.
